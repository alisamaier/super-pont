# Football domain API

Java 25, Spring Boot, Spring Data JPA and Flyway. UUID identifiers are generated by
JPA; Flyway owns schema changes and Hibernate only validates the schema.

## Model

The Java code uses package-by-feature organization under `ro.superpont.football`:
`country`, `competition`, `team`, `season`, `phase`, `round` and `match`. Each
feature organizes its classes into `controller`, `service`, `repository`,
`model` (entities and enums), and `dto` packages.
`ro.superpont.common` contains the shared UUID base entity, page response,
persistence helpers, domain exception and global exception handler. Services
use repositories for related-resource lookups and do not depend on other services.

- A country has competitions and teams. A team's country is its home country,
  not a restriction on which competitions it can enter.
- A competition has seasons; a season has its own participating teams.
- Seasons have configurable phases with a code, display name, ordering, format
  (`LEAGUE` or `KNOCKOUT`) and win/draw/loss point values. These are configuration
  records, not a standings or automatic phase-advancement engine.
- A phase has rounds; each round and match belongs to exactly one season.
- A match references two distinct teams registered in that season. Status and
  optional actual scores describe the match result, not a user's prediction.

No Romanian round counts, playoff qualification rules, score halving, or team
ownership by competition are hardcoded. Phase codes/names are free configuration,
and round numbering is unique within a phase, not across all seasons or phases.
Composite foreign keys also protect season and team-participation boundaries.

## Startup and development data

Use the root README's environment/Compose setup. For development:

```bash
podman compose up -d db
```

Export `SPRING_PROFILES_ACTIVE=dev` and `DATABASE_PASSWORD`, then run
`./gradlew bootRun` here (`.\gradlew.bat bootRun` on Windows). Alternatively,
the existing `podman compose up -d backend` sets the development profile.

The base Flyway location is `db/migration`. Only `application-dev.yml` adds
`db/devdata`. Its repeatable, idempotent sample script creates Romania, SuperLiga,
one explicitly labeled demo season, three configurable phases, eight sample teams,
one round, and four example fixtures. This is not an official fixture schedule.
Without the `dev` profile, a new production database gets the schema only.
Changing profiles does not remove data already inserted into a development
database; use separate development and production databases.

## Authentication

| Method and path | Input and response |
| --- | --- |
| `GET /api/auth/csrf` | Starts or reuses a session and returns `headerName` and `token` (plus `parameterName`). |
| `POST /api/auth/register` | JSON `username`, `email`, `password`. Returns `200` and a profile. Sign in separately. |
| `POST /api/auth/login` | JSON `username`, `password`. Returns `200` and a profile, and rotates the session ID. |
| `POST /api/auth/logout` | Invalidates the session and returns `204`. |
| `GET /api/users/me` | Returns the signed-in profile, or `401`. |

Profiles contain `id`, `username`, `email`, `role`, and `createdAt`.
Usernames use 3–32 ASCII letters, digits, or underscores. Usernames and emails
are stored in lowercase and are unique regardless of capitalization. Passwords
require at least eight characters and allow up to 72 UTF-8 bytes. Accounts
created through registration receive the `USER` role.

Send the session cookie with each request. Before a POST or PUT, call the CSRF
endpoint with the same cookie jar and send the returned token as the
`X-CSRF-TOKEN` header. Get a fresh token after login or logout. Validation errors
return `400`, invalid credentials return `401`, missing or invalid CSRF tokens
return `403`, and registration conflicts return `409` with field messages under
`errors.username` and/or `errors.email`. Both conflicts can appear in the same
response. These field errors disclose which identifiers are already registered.

### Authentication rate limits

| Scope | Default and `prod` | `dev` |
| --- | --- | --- |
| Login per client IP | 5 per rolling minute | 10 per rolling minute |
| Login per case-insensitive username | 5 per rolling minute | 5 per rolling minute |
| Registration per client IP | 3 per rolling 10 minutes | 5 per rolling minute |

Configure each quota with `attempts` and `window` under
`app.auth.rate-limit.login-ip`, `app.auth.rate-limit.login-username`, or
`app.auth.rate-limit.registration-ip`. Windows accept values such as `1m` or
`10m`. Spring loads the development overrides from `application-dev.yml` when
the `dev` profile is active.

CSRF-valid requests count toward the IP limit before body validation. Login
requests that pass IP and body validation also count toward the username limit,
whether the credentials succeed or fail. Rejected requests return `429` with
`Retry-After` in seconds. The frontend displays the wait time.

Each limit keeps up to 10,000 keys in the running backend. Expired keys are
removed as requests arrive. At capacity, new keys wait for an entry to expire.
A restart resets the counters. Multiple backend instances have separate limits.
For a shared limit across instances, enforce it at a trusted gateway or use a
shared rate-limit store.

The default is to use the connection peer IP. Behind a reverse proxy, set
`AUTH_TRUSTED_PROXY_CIDRS` to the comma-separated addresses or CIDRs of proxies
you operate or explicitly trust. The edge must sanitize client-supplied forwarding
headers and forward the real client IP. Restrict direct access to the backend
when deploying behind that edge. Without an allowlist, users behind the same
proxy share its IP limit.

### Football access

Football reads are public. Football writes require an `ADMIN` session and a
valid CSRF token. To create a local admin, register a user and run this SQL
against the local development database with a database operator account:

```sql
UPDATE users SET role = 'ADMIN' WHERE username = 'local_admin';
```

Sign in again after changing the role. Sessions expire after 30 minutes of
inactivity and are stored in the running backend instance.

## Endpoints

Base path: `/api`. JSON request/response bodies use camelCase. Creation returns
`201` and a `Location` header; registration and result updates return `200`.

| Resource | Endpoints |
| --- | --- |
| Countries | `GET /countries`, `GET /countries/{id}`, `POST /countries` |
| Competitions | `GET /competitions?countryId={id}`, `GET /competitions/{id}`, `POST /competitions` |
| Teams | `GET /teams?countryId={id}`, `GET /teams/{id}`, `POST /teams` |
| Seasons | `GET /seasons?competitionId={id}`, `GET /seasons/{id}`, `POST /seasons` |
| Participation | `GET /seasons/{id}/teams`, `POST /seasons/{id}/teams` |
| Phases | `GET /seasons/{id}/phases`, `POST /seasons/{id}/phases`, `GET /phases/{id}` |
| Rounds | `GET /rounds?seasonId={id}`, `GET /rounds/{id}`, `POST /rounds` |
| Matches | `GET /matches?seasonId={id}&roundId={id}`, `GET /matches/{id}`, `POST /matches` |
| Actual result | `PUT /matches/{id}/result` |

Query filters are optional. Top-level lists are paginated: `page=0&size=20`, with
page >= 0 and size between 1 and 100. Responses contain `items`, `page`, `size`,
`totalElements`, and `totalPages`. Phase and season-participant lists are arrays.
Country codes and competition/phase codes are normalized to uppercase.

Create resources in this order, substituting the returned UUIDs:

```text
POST /countries
{"name":"Romania","isoCode":"RO"}

POST /competitions
{"countryId":"<country-id>","code":"RO-SUPERLIGA","name":"SuperLiga"}

POST /teams (repeat for the opponent)
{"countryId":"<country-id>","name":"FCSB","shortName":"FCSB"}

POST /seasons
{"competitionId":"<competition-id>","name":"2026/27","startDate":"2026-07-01","endDate":"2027-06-30"}

POST /seasons/<season-id>/teams (repeat for the opponent)
{"teamId":"<team-id>"}

POST /seasons/<season-id>/phases
{"code":"REGULAR","name":"Regular season","format":"LEAGUE","position":1,"winPoints":3,"drawPoints":1,"lossPoints":0}

POST /rounds
{"phaseId":"<phase-id>","number":1,"name":"Opening round"}

POST /matches
{"roundId":"<round-id>","homeTeamId":"<home-id>","awayTeamId":"<away-id>","kickoff":"2026-11-06T18:00:00+02:00","venue":"Example stadium","status":"SCHEDULED"}

PUT /matches/<match-id>/result
{"status":"FINISHED","homeScore":2,"awayScore":1}
```

Season end cannot precede its start. Kickoff must include a UTC offset, and its
UTC calendar date must be within the season's inclusive dates. Finished matches
require both nonnegative integer scores; live matches may have both or neither.
Scheduled, postponed and cancelled matches must have no scores. Result updates
replace the status and both scores together. Fractional integer fields are rejected.

Invalid requests return `400`, missing references `404`, and duplicate/database
constraint conflicts `409`, using Problem Detail JSON. Field validation errors
include an `errors` object. The API returns DTOs, not JPA object graphs.
Prediction endpoints, deletion and catalog editing are outside this API version.

## Tests

```bash
./gradlew build
```

The normal build applies the same Flyway schema to H2 in PostgreSQL compatibility
mode and runs REST/domain/seed/health tests without external infrastructure.
Dev-seed tests have their own database. To run the REST/domain tests against a
**disposable PostgreSQL database**, export these variables:

```text
TEST_DATABASE_URL=jdbc:postgresql://localhost:<test-port>/football_domain_test
TEST_DATABASE_USERNAME=postgres
TEST_DATABASE_PASSWORD=<test-password>
```

Then run `./gradlew test --tests '*FootballApiTests' --rerun-tasks`.
These tests create test records; use a fresh isolated database, never production.
