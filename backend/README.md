# Football domain API

Java 25, Spring Boot, Spring Data JPA and Flyway. UUID identifiers are generated by
JPA; Flyway owns schema changes and Hibernate only validates the schema.

## Model

The Java code uses package-by-feature organization under `ro.superpont.football`:
`country`, `competition`, `team`, `season`, `phase`, `round` and `match`. Each
feature organizes its classes into `controller`, `service`, `repository`,
`model` (entities and enums), and `dto` packages.
`ro.superpont.common` contains the shared UUID base entity, page response,
persistence helpers, domain exception and global exception handler. Services
use repositories for related-resource lookups and do not depend on other services.

- A country has competitions and teams. A team's country is its home country,
  not a restriction on which competitions it can enter.
- A competition has seasons; a season has its own participating teams.
- Seasons have configurable phases with a code, display name, ordering, format
  (`LEAGUE` or `KNOCKOUT`) and win/draw/loss point values. These are configuration
  records, not a standings or automatic phase-advancement engine.
- A phase has rounds; each round and match belongs to exactly one season.
- A match references two distinct teams registered in that season. Status and
  optional actual scores describe the match result, not a user's prediction.

No Romanian round counts, playoff qualification rules, score halving, or team
ownership by competition are hardcoded. Phase codes/names are free configuration,
and round numbering is unique within a phase, not across all seasons or phases.
Composite foreign keys also protect season and team-participation boundaries.

## Startup and development data

Use the root README's environment/Compose setup. For development:

```bash
podman compose up -d db
```

Export `SPRING_PROFILES_ACTIVE=dev` and `DATABASE_PASSWORD`, then run
`./gradlew bootRun` here (`.\gradlew.bat bootRun` on Windows). Alternatively,
the existing `podman compose up -d backend` sets the development profile.

The base Flyway location is `db/migration`. Only `application-dev.yml` adds
`db/devdata`. Its repeatable, idempotent sample script creates Romania, SuperLiga,
one explicitly labeled demo season, three configurable phases, eight sample teams,
one round, and four example fixtures. This is not an official fixture schedule.
Without the `dev` profile, a new production database gets the schema only.
Changing profiles does not remove data already inserted into a development
database; use separate development and production databases.

## Authentication

| Method and path | Input and response |
| --- | --- |
| `GET /api/auth/csrf` | Starts or reuses a session and returns `headerName` and `token` (plus `parameterName`). |
| `POST /api/auth/register` | JSON `displayName`, `email`, `password`. Returns `200` and pending verification state; sets the limited registration cookie. |
| `POST /api/auth/login` | JSON `email`, `password`. Verified: `200`, profile, and rotated session ID. Unverified with correct credentials: `202` and resumed verification state, without an authenticated session. |
| `GET /api/auth/registration` | Resume status through the registration cookie. Missing/expired token: `401`. |
| `POST /api/auth/registration/confirm` | JSON `code` (six ASCII digits as a string, including leading zeros). Confirms the account; returns `200`. |
| `POST /api/auth/registration/resend` | Issues and emails a replacement code; returns `200` and updated pending state. |
| `POST /api/auth/registration/email` | JSON `email`. Corrects a pending email after uniqueness validation, replaces the code and sends it; returns `200`. |
| `POST /api/auth/password-reset/request` | JSON `email`, normalized as login. Public with CSRF. Always `200` with the same Romanian `message` for known/unknown accounts and SMTP failures; rate limits return `429` and `Retry-After`. |
| `POST /api/auth/password-reset/validate` | JSON `token`. Public with CSRF. `204` for a currently usable link; `400` with `Linkul este invalid sau a expirat. Solicită un link nou.` for an invalid, expired, or used link. Does not consume it. |
| `POST /api/auth/password-reset/confirm` | JSON `token`, `newPassword`. Public with CSRF. Same password rules as registration. `204` consumes all account reset links, revokes sessions, and clears the current session; invalid links return `400`. Requires a new login. |
| `POST /api/auth/logout` | Invalidates the session and returns `204`. |
| `GET /api/users/me` | Returns the signed-in profile, or `401`. |
| `GET /api/users/me/settings` | Returns the saved `hidePredictionsUntilKickoff` boolean for the signed-in account, or `401`. |
| `PUT /api/users/me/settings` | JSON `hidePredictionsUntilKickoff` (required boolean). Session and CSRF required; returns `200` and the saved settings. |
| `PUT /api/users/me/profile` | JSON `displayName`. Session and CSRF required; returns `200` and the updated profile. |
| `PUT /api/users/me/password` | JSON `currentPassword`, `newPassword`. Session and CSRF required; returns `204`, clears the current session cookie, and revokes all previous sessions. |

Password-reset links expire after 30 minutes and carry 256-bit random tokens in
the frontend URL fragment. Flyway V11 stores only SHA-256 hashes, account UUIDs,
expiry, and consumption timestamps. Issuance and reset lock the account row first;
simultaneous uses of the same or different links have one winner. A new request
does not invalidate previous links. Failed SMTP delivery consumes only that
failed delivery's token and allows retry; account data and earlier links survive.
Reset never changes email verification. `User.changePassword` increments the
persisted version checked by `SessionVersionFilter`, revoking sessions across app
instances. See [local recovery and configuration](../README.md#local-password-recovery).

Own-account profiles contain `id`, `displayName`, `email`, `role`, and `createdAt`.
Pending verification responses contain `id`, `email`, `state` (`PENDING` or
`VERIFIED`), `serverTime`, `codeExpiresAt`, `resendAvailableAt`, `attemptsRemaining`,
and `deliveryStatus` (`SENT`, `FAILED`, `NONE`, or `RATE_LIMITED`). No code or token
is returned in JSON. SMTP failures return recoverable pending state rather than
rolling back the account. `codeExpiresAt` is null when delivery failed.

`SP_REGISTRATION` is a 256-bit random HttpOnly cookie, scoped to
`/api/auth/registration`, valid for 24 hours. It uses the session cookie's Secure
and SameSite configuration. Only its SHA-256 hash is stored. It grants no normal
account access. Correct-credential login rotates it without resetting the code,
cooldown, attempts, or hourly send counter. CSRF is required on every write,
including confirmation, resend and email correction.

Codes are cryptographically random, salted BCrypt hashes at rest, expire after
10 minutes, and allow five incorrect attempts. Incorrect codes return `400`
with `code: INCORRECT_CODE` and `attemptsRemaining`; the fifth failure returns
`CODE_ATTEMPTS_EXHAUSTED`, and subsequent attempts return `409` until a new code
is issued. Expired/unavailable codes return `410` with `CODE_EXPIRED`. A successful
confirmation clears the code; retries with the same authorized registration token
return `200`/`VERIFIED` without authenticating. All mutations serialize on the
account's database row, so concurrent resends and confirmations agree on which
code is current. Email corrections flush uniqueness before delivering a message.

Flyway V9 marks all existing accounts legacy verified and changes the database
default to unverified for new accounts. Development demo inserts explicitly set
verified status. The authentication provider and session revocation filter both
require verified email. See the root [Mailpit and SMTP setup](../README.md#local-email-verification-with-mailpit).
Registration and profile updates strip surrounding whitespace and require a
nonblank public name of at most 64 characters. Names are unique after trimming
surrounding whitespace and comparing case-insensitively. The Romanian
UI labels this field **Nume**; changing it does not change the login email.
Ownership and navigation use stable account UUIDs. Leaderboard and other-user
prediction responses contain public names and UUIDs, never email addresses.

Registration and profile name conflicts return `409` with
`errors.displayName: "Display name is already registered"`. Both forms display
**Acest nume este deja folosit. Alege altul.** next to **Nume**. A user can retain
their own name or change only its capitalization. Login continues to use email.

Flyway V10 reserves all existing normalized names, keeps the oldest account's name
in each duplicate group (UUID breaks creation-time ties), and gives the others
available numeric suffixes starting at `2`. Long bases are shortened to keep the
64-character limit; existing names such as `Alisa 2` are not taken away from their
owners. Surrounding whitespace is normalized. Only `display_name` changes;
account IDs, credentials, predictions, points and preferences remain intact.
Every changed name is recorded in `account_name_migration_audit`
(`user_id`, `previous_name`, `new_name`, `changed_at`). PostgreSQL holds an exclusive
user-table lock while repairing names and installing the generated
`display_name_key` unique constraint in the same transaction. The generated key
also protects writes that bypass the application. Application prechecks use the
database's case conversion, matching the constraint's behavior.

Settings are stored separately from the session. Flyway V6 changes the default
to `false` for new accounts without changing any existing saved preferences. Only the session's
account can be updated; no target user ID is accepted as an authority. Settings
responses use `Cache-Control: no-store`. A change applies to every existing and
future prediction on subsequent reads, without changing the editing deadline.

Password changes verify the current password using the existing BCrypt encoder.
The new password follows registration rules (nonblank, 8–72 characters, at most
72 UTF-8 bytes) and is BCrypt-hashed before storage. An incorrect current password
returns `400` without changing credentials or sessions. Account operations determine
the user exclusively from the session, and do not accept another account's ID.

Each session principal records the password version used during authentication.
A successful password change atomically increments the persisted version. A security
filter checks that version on every authenticated request, including across instances
using the same database. Old sessions receive `401` and are invalidated when used;
the changing session is logged out immediately. Re-login requires the new password.
No refresh tokens are used. Already-running requests are not cancelled, and remote
session records may remain until their next request or timeout; they cannot authorize
new requests. This does not replace node-local HTTP sessions with a shared session store.
Registration and login normalize emails with Java `strip()` and lowercase using
`Locale.ROOT`. Registration requires a valid email of at most 254 characters.
The database enforces normalized, nonblank, unique email addresses. Passwords
require at least eight characters and allow up to 72 UTF-8 bytes. Accounts
created through registration receive the `USER` role.

Send the session cookie with each request. Before a POST or PUT, call the CSRF
endpoint with the same cookie jar and send the returned token as the
`X-CSRF-TOKEN` header. Get a fresh token after login or logout. Validation errors
return `400`, invalid credentials return `401`, missing or invalid CSRF tokens
return `403`, and registration conflicts return `409` with field messages under
`errors.email`. This field error discloses whether an email is already registered.

### Migrating existing accounts to email login

Flyway Java migration V7 validates all legacy emails before writing anything. It
reports account UUIDs with missing/invalid emails or duplicate normalized emails
and stops so an operator can resolve those records without merging or deleting
accounts automatically. It normalizes valid emails and copies legacy usernames
into missing public names. V8 then installs the normalized-email constraints and
removes the obsolete username column. Account UUIDs, password hashes, predictions,
points and visibility preferences are preserved.

V7 increments every existing account's password version, requiring a new login
after deployment. Session principals now identify accounts by UUID. No password
reset is needed: sign in with the existing email and password. Take a backup and
resolve any reported conflicts before retrying migration on an existing database.

### Authentication rate limits

| Scope | Default and `prod` | `dev` |
| --- | --- | --- |
| Login per client IP | 5 per rolling minute | 10 per rolling minute |
| Login per normalized email | 5 per rolling minute | 5 per rolling minute |
| Registration per client IP | 3 per rolling 10 minutes | 5 per rolling minute |
| Verification operations per client IP | 30 per rolling minute | Same |
| Code confirmations per registration | 10 per rolling minute | Same |
| Email sends per client IP | 20 per rolling hour | Same |
| Email sends per registration | 6 per hour | Same |

Configure each quota with `attempts` and `window` under
`app.auth.rate-limit.login-ip`, `app.auth.rate-limit.login-email`, or
`app.auth.rate-limit.registration-ip`. Windows accept values such as `1m` or
`10m`. Spring loads the development overrides from `application-dev.yml` when
the `dev` profile is active.

Verification uses `verification-ip` and `verification-registration`; sending uses
`email-ip` and `email-registration` under the same prefix. A 60-second resend
cooldown and a per-registration hourly send counter are also persisted under the
account lock. These survive restarts and token/email changes. SMTP failures consume
send quota. All cooldown and quota rejections return `429` with `Retry-After`.

CSRF-valid requests count toward the IP limit before body validation. Login
requests that pass IP and body validation also count toward the email limit,
whether the credentials succeed or fail. Rejected requests return `429` with
`Retry-After` in seconds. The frontend displays the wait time.

Each limit keeps up to 10,000 keys in the running backend. Expired keys are
removed as requests arrive. At capacity, new keys wait for an entry to expire.
A restart resets the in-memory counters; the persisted registration send counter
and cooldown remain. Multiple backend instances have separate IP limits.
For a shared limit across instances, enforce it at a trusted gateway or use a
shared rate-limit store.

The default is to use the connection peer IP. Behind a reverse proxy, set
`AUTH_TRUSTED_PROXY_CIDRS` to the comma-separated addresses or CIDRs of proxies
you operate or explicitly trust. The edge must sanitize client-supplied forwarding
headers and forward the real client IP. Restrict direct access to the backend
when deploying behind that edge. Without an allowlist, users behind the same
proxy share its IP limit.

### Football access

Football schedule reads are public. Schedule and result writes require an
`ADMIN` session and a valid CSRF token. To create a local admin, register and verify a user, then run this SQL
against the local development database with a database operator account:

```sql
UPDATE users SET role = 'ADMIN' WHERE email = 'local_admin@example.test';
```

Sign in again after changing the role. Sessions expire after 30 minutes of
inactivity and are stored in the running backend instance.

## Endpoints

Base path: `/api`. JSON request/response bodies use camelCase. Creation returns
`201` and a `Location` header; registration and result updates return `200`.

| Resource | Endpoints |
| --- | --- |
| Countries | `GET /countries`, `GET /countries/{id}`, `POST /countries` |
| Competitions | `GET /competitions?countryId={id}`, `GET /competitions/{id}`, `POST /competitions` |
| Teams | `GET /teams?countryId={id}`, `GET /teams/{id}`, `POST /teams` |
| Seasons | `GET /seasons?competitionId={id}`, `GET /seasons/{id}`, `POST /seasons` |
| Participation | `GET /seasons/{id}/teams`, `POST /seasons/{id}/teams` |
| Phases | `GET /seasons/{id}/phases`, `POST /seasons/{id}/phases`, `GET /phases/{id}` |
| Rounds | `GET /rounds?seasonId={id}`, `GET /rounds/{id}`, `POST /rounds` |
| Matches | `GET /matches?seasonId={id}&roundId={id}`, `GET /matches/{id}`, `POST /matches` |
| Actual result | `PUT /matches/{id}/result` |
| My predictions | `GET /predictions/me`, `PUT /matches/{matchId}/prediction`, `DELETE /matches/{matchId}/prediction` |
| SuperLiga leaderboard | `GET /leaderboard/superliga` |

Query filters are optional. Top-level lists are paginated: `page=0&size=20`, with
page >= 0 and size between 1 and 100. Responses contain `items`, `page`, `size`,
`totalElements`, and `totalPages`. Phase and season-participant lists are arrays.
Country codes and competition/phase codes are normalized to uppercase.

### SuperLiga leaderboard

`GET /api/leaderboard/superliga?page=0&size=20` requires a signed-in session. It returns a page of entries with
`rank`, `userId`, `displayName`
and `totalPoints`. The server
selects Romania's `RO-SUPERLIGA` season covering the current UTC date. If
season dates overlap, the latest start date wins. With no current season or
registered accounts, the page is empty. Every registered account appears in the
current-season leaderboard, including accounts without predictions or evaluated
results, starting at zero points. New registrations appear on the next read.

Points come from the current final results in that season. Users with the same
total share a rank (for example 1, 2, 2, 4). Totals and ranks are calculated
in the database across the whole selected season before `LIMIT` / `OFFSET`.
Only points determine rank. Display order is points descending, then
case-insensitive display name ascending and stable user UUID ascending.
Rank applies across pages, including ties at page boundaries.

The response is `PageView`: `items`, zero-based `page`, `size`, `totalElements`
(all registered users), and `totalPages`. The default size is 20. Negative
pages, noninteger parameters, and sizes outside 1–100 return `400`.
An out-of-range page returns empty `items` and the actual totals, allowing the
client to navigate to the last available page.

`GET /api/leaderboard?competitionId={uuid}&seasonId={uuid}&page=0&size=20`
uses the same query for an explicitly selected competition and season.
The season must belong to that competition; a missing or mismatched season
returns `404`. It also requires a signed-in session. The corresponding
`GET /api/leaderboard/users/{userId}/predictions?competitionId={uuid}&seasonId={uuid}`
returns that user's predictions and total for the same selection, with the
same pagination and visibility rules as the SuperLiga route below.

`GET /api/leaderboard/superliga/users/{userId}/predictions?page=0&size=20`
also requires a signed-in session and returns the selected user's display name, competition and season names and IDs,
current-season `totalPoints`, `serverTime`, and a `predictions` page.
Matchdays appear in reverse phase and round order, with later kickoffs first.
An unknown user or missing current season returns `404`.

Each prediction includes the teams, match and round IDs, round and phase labels,
kickoff, status, visibility, and evaluation `result`. Before kickoff, visibility
is `HIDDEN` when the owner has `hidePredictionsUntilKickoff=true`; `predictedScore`
is omitted and `result` is null. With the setting disabled, saved scores are
`REVEALED` immediately with `predictedScore: {"home":3,"away":2}`. At kickoff,
scores are revealed regardless of the preference, using the same server-clock
boundary as prediction writes. An authenticated owner always sees their own
scores, including on this endpoint; send the session cookie for that exception.
Unauthenticated GET and HEAD requests to either endpoint return `401`, including
after logout. Send the session cookie from the frontend. Responses use `no-store`,
and each request reads the owner's persisted preference.

`result` is `null` while evaluation is pending. A finished match with both
scores returns `result: {"homeScore":5,"awayScore":0,"points":10}`. Zero points
are an evaluated result. The total and evaluation use the existing scoring
formula and the latest stored match results.

### Predictions

`GET /api/predictions/me` returns a page of the signed-in account's predictions.
Each item contains `id`, `matchId`, `homeScore`, `awayScore`, `createdAt`, and
`updatedAt`. Reads still include predictions after kickoff. The `result` field
is `null` until the match is `FINISHED` with both scores. It then contains the
final `homeScore`, `awayScore` and total `points` (0–10). Each read uses the
current result from the match, including any corrections submitted through
`PUT /api/matches/{id}/result`.

Send `{"homeScore":0,"awayScore":2}` to `PUT /api/matches/{matchId}/prediction`
with the session's CSRF header. Both values must be JSON integers between 0 and 99.
The first save returns `201` with a `Location` header. Updating the same match
returns `200` and preserves the prediction ID and creation time. The server
identifies the account from the session.

`DELETE /api/matches/{matchId}/prediction` also requires the CSRF header and
returns `204` before kickoff, including when the account has no prediction for
the match. Both write endpoints return `409` once server time reaches kickoff
and `404` for an unknown match. Invalid scores return `400`.

### Creating football fixtures

Create resources in this order, substituting the returned UUIDs:

```text
POST /countries
{"name":"Romania","isoCode":"RO"}

POST /competitions
{"countryId":"<country-id>","code":"RO-SUPERLIGA","name":"SuperLiga"}

POST /teams (repeat for the opponent)
{"countryId":"<country-id>","name":"FCSB","shortName":"FCSB"}

POST /seasons
{"competitionId":"<competition-id>","name":"2026/27","startDate":"2026-07-01","endDate":"2027-06-30"}

POST /seasons/<season-id>/teams (repeat for the opponent)
{"teamId":"<team-id>"}

POST /seasons/<season-id>/phases
{"code":"REGULAR","name":"Regular season","format":"LEAGUE","position":1,"winPoints":3,"drawPoints":1,"lossPoints":0}

POST /rounds
{"phaseId":"<phase-id>","number":1,"name":"Opening round"}

POST /matches
{"roundId":"<round-id>","homeTeamId":"<home-id>","awayTeamId":"<away-id>","kickoff":"2026-11-06T18:00:00+02:00","venue":"Example stadium","status":"SCHEDULED"}

PUT /matches/<match-id>/result
{"status":"FINISHED","homeScore":2,"awayScore":1}
```

Season end cannot precede its start. Kickoff must include a UTC offset, and its
UTC calendar date must be within the season's inclusive dates. Finished matches
require both nonnegative integer scores; live matches may have both or neither.
Scheduled, postponed and cancelled matches must have no scores. Result updates
replace the status and both scores together. Fractional integer fields are rejected.

Invalid requests return `400`, missing references `404`, and duplicate/database
constraint conflicts `409`, using Problem Detail JSON. Field validation errors
include an `errors` object. The API returns DTOs, not JPA object graphs.
Prediction endpoints, deletion and catalog editing are outside this API version.

## Tests

```bash
./gradlew build
```

The normal build applies the same Flyway schema to H2 in PostgreSQL compatibility
mode and runs REST/domain/seed/health tests without external infrastructure.
Dev-seed tests have their own database. To run the REST/domain tests against a
**disposable PostgreSQL database**, export these variables:

```text
TEST_DATABASE_URL=jdbc:postgresql://localhost:<test-port>/football_domain_test
TEST_DATABASE_USERNAME=postgres
TEST_DATABASE_PASSWORD=<test-password>
```

Then run `./gradlew test --tests '*FootballApiTests' --rerun-tasks`.
These tests create test records; use a fresh isolated database, never production.
